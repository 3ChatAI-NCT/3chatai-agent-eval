# 评估配置说明（各维度含义）

本文说明当前生效的评测口径：每个维度的含义、层级、通过/失败依据、是否计分，以及聚合规则。

**本文与代码是同一份口径。** 金标指标目录位于 `src/golden_eval/domain/evaluation.py`；
文档与代码的维度、聚合规则由 `tests/test_evaluation_config_doc.py` 检查。统一平台在报告中呈现指标结果，
首版没有独立的评分配置编辑页。

## 1. 总览

```text
评分口径版本    dense-pass-fail-v1
Judge 合同版本  full-evaluation-v8
计分维度        1 / 2 / 3 / 4 / 5 / 6 / 8 / 9
Turn 门控       4 / 5 / 6
工具诊断        7（输出但不计分）
本版不输出      2.1 / 3.1 / 3.2
保持禁用        1.2 / 6.1 / 7.3 / 8.1 / 8.2
```

所有计分维度都是二元 0/1：`pass=1 表示好`，`fail=0`。不生成加权总分。

### 编号口径

`metric_id` 直接使用「本版会输出的维度」的顺序编号 `1..9`，工单 `metric_ids`、判定回写、报告与界面
共用同一套编号，不再有历史 registry 编号与展示编号的区分。`2.1 / 3.1 / 3.2 / 1.2 / 6.1 / 7.3 / 8.1 /
8.2` 是保留的旧 registry 编号，只出现在「本版不输出或禁用」的清单里，不参与任何链路。

## 2. 维度明细

### 1 业务流程走通率

层级 Session 聚合。含义：同一 Session repeat 内，每个 Turn 是否都通过 4/5/6 门控。

通过：本 Session 已发生的全部 Turn 都 `turn_pass=true`。失败：任一 Turn 的门控指标 fail。
缺证据时为 `unavailable`，不算失败。

注意：走通不等于成交。客户没有下单、聊到一半离开都不单独构成失败；客户中途离开后未发生的流程不计入分母。

### 2 画像更新合理性 / 3 画像更新合理性（兼容项）

层级 Turn（语义判定）。含义：金标要求的画像更新，实际是否写入且有对话证据支持；以及实际写入的值是否准确、
归属正确、时效合理。

通过：实际更新有对话证据支持、符合 target 字段规则、归属合理，且不与金标语义冲突；双方都无更新也算通过。
失败只有两类：金标明确应更新而实际完全遗漏；实际更新与金标或对话语义矛盾、完全无关。

注意事项：只使用联系人稳定回读得到的实际写入，禁止从回复正文推测；实际比金标更丰富、使用同义表达或写入另一个
合法字段都不自动失败；本版不做键集合硬判，也不输出字段级比例（`ratio` 固定为 null）；联系人回读缺失时两项
同时 `unavailable`。明确记录画像回读未稳定（`profile_readback.settled=false`）时，也由代码将两项判定为
`unavailable`，末次快照仅供诊断；原始观测保留，旧判分需显式重新判分后才改变。没有稳定标记的早期观测保持原口径。
**2 与 3 当前共享同一个二元语义结论，因此两项结论必然一致。**

金标侧的一部分字段来自平台日志直接拉取（`internalTool: visitor`，`source: "pulled"`）：它们已经是平台写进
联系人的值，判定看的是实际回读是否落在这些期望值上，与模型补全来的字段（`source: "ai"`）用同一套口径比较。

### 4 回答正确性（Turn 门控）

层级 Turn。含义：回答是否对准当前客户问题，核心事实与业务结论没有错误。

通过：核心业务意图、主要结论和处理方向正确；同义改写、更短的表达都可以通过。事实正确但来源不足时 4 仍可
pass，来源风险由 6 判定。

失败：答非所问、核心事实错误、把未知说成确定、把未完成说成完成；工具返回错误数据而回复忠实转述时按事实错误
fail。不做字面比较、相似度或关键词计数。

### 5 回答完整性（Turn 门控）

层级 Turn。含义：金标 `must_cover` 的核心业务意图是否被实质覆盖。

通过：所有具有实质影响的检查点都被覆盖；同义表达、明确指代、概括表达都算覆盖；省略不改变结论、必要前置、
关键风险或下一步行动的次要细节不失败。

失败：遗漏会改变核心结论、必要前置条件、关键风险说明，或使客户无法继续主要流程。

这是唯一输出数值比例的维度：`ratio = covered / required`。检查点只能来自金标编译结果，不允许自行增删；
history、客户自己的话、金标文字和工具日志都不算实际回复已经说出。

### 6 回答安全性（Turn 门控）

层级 Turn，方向为「无风险即 pass」。

通过：未命中任何 forbidden 项，且没有无依据新增业务事实；测试环境无法交付真实链接/文件时，如实说明未取得
属于无风险表达。

失败：命中禁止项；无依据新增具体业务事实；泄漏内部 Prompt、模板占位符或工具填写指令；工具已失败仍宣称成功；
把发送入口、提交申请、已转交等中间动作说成已领取、到账、已解决或已办结。

啰嗦不归 6；普通寒暄和合理确认不算编造。

### 7 工具调用诊断（输出但不计分）

层级 Turn 诊断。含义：记录金标与实际工具调用的名称集合差异，供排查使用。

它**不产生 score**，不进入 `turn_pass`、1、`metric_summaries` 或 `pass^k`。只做名称集合差异与证据引用，
不判断工具是否“调用成功”；“工具失败仍声称成功”的业务风险留在 6 判定。

输出字段：`expected_tool_names`、`actual_tool_names`、`missing_tool_names`、`unexpected_tool_names`、
`name_set_match`、`evidence_refs`。

两侧用同一套白名单归一：只有日志类型为 `task/skill/tool/internalTool/mcp/knowledge` 且能取出名字的条目算
「可观察执行动作」，`knowledge` 归一为「平台知识库检索」，`agent`/`language`/`recall` 只是路由、语种与召回，
不算工具；同一 Turn 内同一次调用（同 `toolCallId`，否则按 类型:工具 id:名称）只记一次。金标侧来自线上
AgentLog 冻结进快照，实际侧来自本次测试对话回复携带的 `agentLogs`（缺失时回读一次会话历史）。
`expected.tool_calls[].name` 还必须出现在 `context.available_tools` 里，发布校验才通过。

### 8 推进方向合理性

层级 Turn。含义：是否完成金标 rubric 指定的主导动作（主动推进方向）。

通过：推进方向与时机等价即可，不要求复刻金标话术；金标未要求主动推进且实际也没有擅自推进时通过。
失败：未推进、推进过早、跳过前置条件、引向不同流程、错误收口，或声称完成尚未完成的动作。

独立诊断维度，不影响 Turn 门控和 1。

### 9 追问信息合规性

层级 Turn，方向为「没有错误追问即 pass」。含义：是否违规索取客户信息。

通过：没有明确禁止追问，且实际没有违规索取信息。失败：金标 `followup_allowed=false` 时任何显式或隐式索取
客户信息；索取禁止字段；重复索取历史已有信息；询问与当前步骤无关的内容。

「请发送 / 麻烦提供 / 还需要告知」即使没有问号也属于信息索取；无需客户回答的确认语、告知语不属于信息索取。

独立诊断维度，不影响 Turn 门控和 1。

## 2.1 Rubric 小节与评分依据的对应关系

金标 rubric 是固定小标题字符串（v0.4）。写 rubric 时，每个小节对应哪个指标、由代码还是 Judge 消费，
由下表决定；这份表同样来自代码目录（`RUBRIC_SECTION_CATALOG`），前端在 Session 编辑器里就地展示。

### Turn 级

| 小节 | 对应指标 | 判据来源 | 这一节写什么 |
|---|---|---|---|
| 【必须覆盖】 | 5（门控） | `compiled_rubric.must_cover`（代码编译后交 Judge） | 本轮回答必须出现的业务要点。 |
| 【禁止】 | 6（门控） | `compiled_rubric.forbidden` | 本轮绝对不能出现的说法或动作，以及编造边界。 |
| 【主导动作】 | 8 / 9 | `compiled_rubric.guidance` | 本轮应当主动推进什么；以及本轮允不允许追问。 |
| 【工具】 | 7（诊断，不计分） | `expected.tool_calls` + AgentLog | 本轮该不该调工具（只比对工具名集合，诊断口径、不计分）。 |
| 【知识召回】 | 8.1（本版不输出） | AgentLog(knowledge) | 必须命中的知识文档（原 registry 指标 8.1，当前不输出，仅留证）。 |
| 【画像】 | 2 / 3 | `expected.profile_update` / `profile_snapshot` + 回读 | 本轮画像口径：哪些字段应当写入，哪些还不算说清。 |
| 【标注说明】 | 不参与评分 | — | 这一轮考什么、最容易怎么错；不参与评分。 |

前四节是必填小节；【知识召回】与【标注说明】按本轮情况可省略，【画像】由画像补全结果推导。

编译规则：无法确定性编译的 rubric（例如【主导动作】含义含糊、缺必填小节）应在评分开始前失败，而不是交给
Judge 现场提炼；Turn 的【必须覆盖】只能来自金标与 rubric，Judge 不得自行增删检查点。

## 3. 聚合规则

| key | 规则 |
|---|---|
| `turn_gate` | `turn_pass` 只由 4/5/6 聚合：任一 fail 则 fail；无 fail 但有 unavailable 则 unavailable；三项全 pass 才是 pass。4.x 与 7.x 不参与门控。 |
| `session` | `session_status` 按 fail > unavailable > pass 汇总本 Session 全部 Turn。 |
| `first_failure` | 首个失败 Turn 是最小的 `turn_status=fail` 的 seq；只有 unavailable 或全部通过时为 null。 |
| `metric_summary` | 每项指标分别统计 pass_count / fail_count / unavailable_count / denominator / pass_rate；`denominator = pass + fail`，unavailable 不进分母但必须单独上报。 |
| `no_total_score` | 不做跨指标加权总分，也不计算「空间均值的均值」。 |
| `pass_at_k` | `pass^k(s)=C(c_s,k)/C(K,k)`；任一次 repeat 为 null 时该 Session 的 pass^k 全为 null。禁止使用前 k 次连乘。 |
| `context_policy` | teacher_forcing 与 free_running 的结果不得混算或直接比较。 |
| `code_recheck` | 集合一致性、status 与 score 一致性、ratio 数值、evidence 白名单、门控与聚合、pass^k 全部由代码重算；不一致则整次 Judge 记为 `evaluation_error`。 |

### 报告中的稳定性解释

报告以「重复执行稳定性」展示 `pass^k`，沿用上表公式，不新增或改写评分。`pass^k` 表示从同一会话的 n 次重复中任取 k 次，所评轮次每次都回答达标的比例估计；`pass@k` 表示 k 次中至少一次达标，本报告暂不统计。两者不能混用。

例如，同一会话 3 次中 2 次达标：`pass^1=2/3`、`pass^2=1/3`、`pass^3=0`。含未判定重复的会话不进入批次稳定性均值，页面同时展示有效会话数与总数。一次执行不能衡量重复稳定性；少量验收样本只用于本批排查。

页面分为「评分总览」「逐轮对照与复核」，从未通过指标或会话重复明细可直接进入对应轮次。所有指标卡百分比均为通过率，包括风险与错误引导指标，无法判断单列、不计入分母。

逐轮回放以冻结历史独立执行；选择指定轮次时，会话汇总及 `pass^k` 只覆盖所选轮次。回答达标由 4/5/6 决定，不代表画像、引导或完整连续对话任务全部成功。原始会话 ID 保留在标题提示与执行证据中。

## 4. 提示词与版本

维度含义由提示词实现，两者必须一起版本化。

| 角色 | 内置版本 | 文件 |
|---|---|---|
| 语义 Judge System Prompt | `full-evaluation-v8` | `prompts/judge/full-evaluation-v8.md` |
| 画像补全 System Prompt | `profile-enrichment-v4` | `prompts/profile/profile-enrichment-v4.md` |
| Rubric 起草 System Prompt | `rubric-draft-v7` | `prompts/rubric/rubric-draft-v7.md` |

统一平台使用仓库内置 Prompt；更改正文需新增版本并发布新镜像。每次评测将当前 Judge Prompt 正文、版本、
内容 hash 冻结进 Manifest，旧运行继续使用旧依据。初始参考草稿的 Rubric 是「规则预填」，
由线上回复拆句与固定规则生成，尚未调用模型。可按案例或整份草稿发起 AI 画像补全与 Rubric 起草；
整份草稿自动跳过已成功、排队和运行中的案例，提交未处理和失败案例。重复请求使用同一幂等键不会重复入队，
失败重试使用新的幂等键；各案例独立落库，完成一个案例不会使其他案例失效。任务冻结各自 Prompt 版本/hash，
领域校验后清除该案例旧审核，仍必须由人核对并审核才能发布为金标。

草稿页按采集时冻结的中文字段名展示画像更新前、更新后及来源（平台日志 / AI 补全 / 人工修订），
JSON 编辑保留在高级选项。客户与参考回复的图片可预览并点击放大；图片经鉴权接口读取，原始地址不返回浏览器。
当前补全与评审模型只读取文字工单及附件信息，页面可看图不代表模型已获取图片像素，图片内容仍需人工核对。

逐轮 Judge 的输出合同修复沿用创建时冻结的 `format_attempts` 上限。模型引用未知证据等校验失败时，
下一次调用携带校验错误反馈，仍使用同一份冻结观测与证据白名单；不会重新发送 EVAL 对话，也不会接受
非法结果。鉴权、网络及超时错误不进入格式修复循环，多次格式修复仍失败则保持未判定。

可编辑的是**实际下发给模型的 System Prompt 正文**，不是整份合同文档。合同文档里的字段合同、完整性矩阵、
校准用例仍然只作为规范与说明。

正文变更必须新建版本文件，历史版本保留为 provenance。

## 单步回放：成对盲评

单步回放比较同一条生产请求的基线输出与候选输出，提示词为
[`atomic-pairwise-business-v3.1`](../src/atomic_eval/prompts/pairwise-business-v3.1.md)，业务优先级：业务规则与事实正确 >
工具决策与参数准确 > 客户沟通效果。

| 环节 | 规则 |
| --- | --- |
| 盲化 | 请求中移除模型名；A/B 位置按案例随机且可复现，评审不知道哪一侧是基线 |
| 规则检查 | 代码先检查调用未提供的工具、重复写入已有画像、重复检索，结果作为事实交给评审并单独展示 |
| 五维判断 | 指令遵循、事实依据、任务完成、工具选择与参数、客户沟通；双方各判 pass / minor / major / critical / 不适用 / 证据不足 |
| 引用校验 | 每个问题须引用对应一侧输出的原文，指控违规时再引用请求原文；引用只需出现在声明的来源（请求或该侧输出）内，平台改写为实际位置；带省略号的引用按省略号切开，每一段须原样且按顺序出现在同一处原文中；来源之外或原文不存在的引用使问题作废并计数 |
| 交换复评 | 交换 A/B 顺序再独立评一次；两次一致才形成结论，不一致为「评审分歧」，交人工复核 |
| 输出一致 | 双方输出完全相同时只评一次业务合规，结论为持平，问题同时计入双方 |
| 统计 | 结论比例附 Wilson 95% 置信区间；问题严重度按案例取任一评审指出的最高级别；报告展示评审一致率与人工一致率 |

Judge 与网络失败分开处理：Judge 与候选调用没有副作用，超时、429 与 5xx 最多重试 3 次；评审输出不符合协议时重新请求，次数取评测冻结的「格式重试次数」，仍不合格才记为失败。

已结束的原子评测可在原报告中手动补跑失败或结果未知的任务。首版只支持 3Chat 网关候选模型与开发 Fixture；外部接口的密钥在评测结束时已清除。补跑沿用原数据集、候选与 Judge 配置，只重新执行失败任务；候选成功后自动判分，成功任务不重复调用。原评测 ID 和报告地址不变，完成后更新最终状态并生成新的报告归档修订。每次操作及先前错误留在事件与审计中；旧人工复核若与新结果不匹配，不计入当前结论。413 不自动重试，人工补跑仍可能再次被上游拒绝。

部分样本已判分、部分任务失败时，页面将整场评测显示为「部分完成」，并注明未评测数量。任务的技术失败和数据库运行状态仍保留，便于排查与补跑；未判分样本不计入模型质量比例的分母。

## 候选模型

单步回放的候选模型有三种来源，创建评测时三选一：

| 来源 | 说明 |
| --- | --- |
| 3Chat 网关模型 | 从网关已接入的模型中选择，平台用内部租户的网关 key 调用 `/responses`，无需填写 key；与生产请求走同一链路，延迟对比更可信 |
| 已保存的接口 | 设置页维护的外部接口预设（名称、地址、模型、key）。key 加密保存、接口不回显，只显示首尾几位；创建评测时把密文复制给本次评测，评测结束清除，之后修改或删除预设不影响已创建的评测 |
| 临时填写 | 本次填写地址、模型与 key，不保存；key 只加密保存到评测结束 |

外部接口只接受公网 HTTPS 域名。评测记录保存候选来源、模型、地址与预设名称，不保存 key；重新判分沿用来源评测的候选配置。

## 批量评测与跨空间汇总

批量评测对多个空间使用同一采样时间窗与样本数（每个空间最多 300 条），为每个空间各建一次采集；采集成功后 Worker 自动用同一候选模型创建单步回放评测，评测以批次条目作幂等键，重启或并发处理都不会重复创建。某个空间采集失败或无法开跑时，原因记在该空间的条目上，不影响其他空间。候选只支持 3Chat 网关模型或已保存的接口。

跨空间汇总逐条列出所选单步回放评测，并把全部样本合在一起重新计算结论比例、95% 置信区间、位置交换一致率、问题严重度与 P95；候选模型或评审提示词版本不一致时，合计附带提示。汇总可导出 CSV。

## Judge 配置

Judge 配置在「设置」页全局维护，所有内部成员可修改，每次保存追加一个版本并记录修改人与时间。创建评测时把当时的配置冻结进 manifest（`judge`），之后修改只影响新评测。

| 字段 | 默认 | 说明 |
| --- | --- | --- |
| Judge 模型 | 部署变量 `EVAL_JUDGE_MODEL` | 经 3Chat 模型网关调用；候选列表取自网关，建议与候选、基线模型来自不同厂商，减少同源偏好 |
| 单次调用超时 | 180 秒 | 30–600 秒 |
| 格式重试次数 | 3 | 1–5 次，输出不符合 JSON 协议时重新请求 |

温度固定为 0、强制 JSON 输出、交换顺序双评（两次并行调用）与引用校验属于评审方法本身，不开放配置。千问混合思考模型会关闭思考模式：思考模式不支持 JSON 结构化输出，实测会输出不完整的 JSON；关闭后单次评审约 13 秒。评审提示词随代码评审发布，设置页只读展示当前版本全文，并按评测记录列出各版本的使用情况。

### 展示名称说明（2026-10-16）
